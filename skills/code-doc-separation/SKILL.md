# 代码与文档解耦

## 目标

让代码和文档按职责组织。可以在同一次变更或同一个提交中更新代码和文档，但不要因为它们同时变化，就把可独立维护的内容合并到同一文件、模块或文档中。

优先遵守仓库已有的目录约定、模块边界、文档格式和生成流程。本 skill 不用文件数量、目录层级或行数代替职责判断。

## 修改前

1. 阅读仓库级和目标目录的规则文件，例如 `AGENTS.md`、`CONTRIBUTING.md` 以及本地 README。
2. 阅读目标代码、相关测试、文档入口和已有的权威说明。
3. 将计划中的内容分类为：
   - 业务代码
   - 接口或适配器代码
   - 测试代码
   - API 或配置契约
   - 使用指南
   - 接口参考
   - 设计说明或决策记录
   - 排障和运维说明
   - 生成文件
4. 修改前先建立边界。对每个拟修改文件说明其主要职责、依赖方向和权威内容。发现两部分内容的变更原因、读者或替换方式不同，就优先拆分。
5. 如果拆分会违反项目既有约定，或事实不足以确定边界，先提出一个具体问题。无法提问时，明确写出假设和保留的耦合原因。

## 代码边界

- 一个模块保持一个主要职责。入口、组装器或组合根可以负责连接模块，但不要在其中堆积各层实现。
- 将可以独立测试、复用或替换的职责分开，通过明确的接口或稳定的数据结构协作。
- 按项目实际使用的架构分离表示层、业务规则、用例编排、外部服务、存储访问和适配器。不要为了套用固定分层而机械新增目录。
- 不让界面层直接访问数据库实现，不让领域规则依赖 HTTP、文件系统或具体 SDK，除非项目的现有边界明确要求这样做。
- 不把无关功能放进含义模糊的 `utils`、`common` 或 `helpers`。如果辅助代码只有一个清晰的调用方，可以保留在该模块附近。
- 不因为本次任务同时涉及两个功能，就把两个功能塞进同一个文件。
- 不为减少文件数量而合并独立职责，也不为满足行数阈值而制造只有转发作用的模块。
- 保持现有公共 API、配置键、命令和错误语义。必须改变时，更新相应契约和测试。

## 文档边界

- 每篇文档只保留一个主要主题和一类主要读者。
- 将以下内容分开维护，除非项目已有明确的共置约定：
  - 操作步骤与快速开始
  - API、CLI、配置和数据格式参考
  - 架构说明与设计决策
  - 故障排查和运维手册
  - 版本变更记录
- 入口 README 负责概览、最短上手路径和导航。不要把完整 API 参考、长篇设计讨论或所有排障记录追加到 README。
- 同一事实只保留一个权威位置。其他文档使用链接、引用或简短摘要，不复制一份需要同步维护的完整内容。
- 源码注释只说明局部契约、不变量、非显而易见的原因和限制。不要把教程、运维手册或长篇设计说明写进源码注释。
- 文档中的命令、路径、配置键、接口名称和代码标识符必须与实际实现一致。可执行示例优先引用真实代码，或通过测试、编译和类型检查验证。
- 生成的文档和代码必须遵守项目的生成流程。不要直接编辑生成文件来绕过源文件。

## 代码与文档的关系

- 代码负责执行行为。文档负责说明使用方式、公开契约、设计原因和运维操作。
- 公共行为、配置、命令或错误语义发生变化时，更新对应的权威文档和测试。
- 不把完整生产实现复制到文档作为第二套维护对象。文档只保留能帮助读者完成任务的最小示例。
- 不让文档替代接口边界，也不让注释替代测试。用类型、接口、测试和校验表达可执行约束；用文档解释读者需要知道的背景和操作。
- 代码和文档可以在一个提交中一起更新，但在计划、编辑和验证时按两个工作面管理。提交说明应能区分代码行为变化和文档变化。

## 执行流程

1. 列出拟修改的代码文件、文档文件和测试文件，并为每个文件写一句职责说明。
2. 确认每条事实的权威来源。优先复用现有模块和文档，不新增重复实现或重复说明。
3. 先建立或修正边界，再实现行为变化。避免在重构无关模块的同时扩大任务范围。
4. 让依赖方向清晰。检查是否出现跨层直接引用、循环依赖、隐藏的全局状态或通过复制文档来同步信息的做法。
5. 验证代码。按项目约定运行测试、类型检查、构建、lint 或依赖边界检查。
6. 验证文档。检查链接、命令、路径、配置键、接口示例和导航。对关键示例运行项目提供的校验。
7. 阅读最终 diff，确认没有职责混合、事实重复、过期说明或未说明的例外。

## 交付说明

完成时按以下顺序报告：

1. 代码、测试和文档分别改了什么。
2. 新的职责边界和每条事实的权威位置。
3. 运行了哪些验证，结果是什么。
4. 哪些内容仍然共置，以及共置的具体原因。
5. 未解决的事实问题、兼容性风险或后续工作。

不要仅用“已解耦”“结构更清晰”作结论。指出实际文件、接口、依赖方向和验证结果。

## 允许共置的情况

以下情况通常可以共置：

- 只服务于当前模块且很短的局部辅助函数。
- 与接口绑定的短注释、类型说明和不变量。
- 与测试绑定的测试夹具和最小示例。
- 框架明确要求的组件、样式、测试或文档共置结构。
- 生成流程要求放在一起的源文件。

如果共置内容以后可能由不同人员、不同发布节奏或不同依赖方独立修改，重新评估边界，并在交付说明中记录决定。

## 不要采用的做法

- 用文件行数、文件数量或目录深度作为唯一拆分依据。
- 把 UI、业务规则、数据库访问和外部 API 调用写进同一个大文件。
- 把使用指南、接口参考、设计讨论和排障记录全部堆进 README。
- 在多个文档中复制同一份配置表、接口定义或完整代码。
- 用 `utils`、`common` 或 `misc` 隐藏未定义的职责边界。
- 为了看起来解耦而创建大量无行为、无稳定边界的转发文件。
- 在没有检查实际实现的情况下编写或修改文档。
- 在没有验证的情况下声称代码、示例或文档已经正确。
